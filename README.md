# cyberdocs

Особиста база знань з кібербезпеки: статті, приватні інструменти (з командами)
та приватні замітки, плюс інтерактивний roadmap. Next.js 16 (App Router) +
React 19 + TypeScript + Tailwind CSS. Дані — у Postgres (Supabase, безкоштовний
tier), авторизація — теж Supabase Auth.

## Модель доступу

- **Статті** — публічні. Доступні й редагуються без входу (за бажанням —
  захистіть це спільним токеном, див. нижче).
- **Інструменти та замітки** — приватні. Потрібен вхід; кожен користувач бачить
  і редагує тільки своє. Ізоляція забезпечена на рівні бази (Row Level
  Security), а не лише кодом застосунку.
- **Базовий контент** (7 стартових статей, каталог типових security-інструментів,
  шпаргалка команд, roadmap) — вбудований у репозиторій, видний усім завжди,
  редагується тільки через файли в `content/`.

## Швидкий старт

### 1. Створіть безкоштовний проєкт Supabase

1. Перейдіть на https://database.new — це створює новий проєкт Supabase
   (безкоштовний tier: 500 МБ бази, достатньо з запасом для особистого проєкту).
2. Дочекайтесь ініціалізації проєкту (1–2 хвилини).
3. Відкрийте **SQL Editor** → **New query**, вставте вміст файлу
   [`supabase/schema.sql`](./supabase/schema.sql) з цього репозиторію і
   натисніть **Run**. Це створює три таблиці (`articles`, `tools`, `notes`)
   і політики Row Level Security.
4. Відкрийте **Project Settings → API** і скопіюйте:
   - **Project URL**
   - **anon / public key**

### 2. Налаштуйте змінні середовища

```bash
cp .env.example .env.local
```

Впишіть у `.env.local` значення з кроку вище:

```
NEXT_PUBLIC_SUPABASE_URL=https://xxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...
```

### 3. Запустіть проєкт

```bash
npm install
npm run dev
```

Відкрити http://localhost:3000

## Реєстрація та вхід

За замовчуванням Supabase вимагає підтвердження email при реєстрації —
на вказану пошту прийде лист з посиланням (обробляється маршрутом
`/auth/confirm`). Для особистого проєкту, де email-доставка не критична,
можна вимкнути цю вимогу: **Authentication → Providers → Email → Confirm
email → вимкнути**. Тоді після `signUp` одразу видається сесія, без листа.

Я написав увесь код авторизації за офіційним патерном Supabase (`@supabase/ssr`,
`getClaims()`, `proxy.ts` для оновлення сесії), але не мав змоги протестувати
живий вхід/реєстрацію без реального Supabase-проєкту — тестування логіки з
власними кредами варто зробити самостійно одразу після налаштування.

## Деплой на Vercel

1. Запуште репозиторій у GitHub.
2. На vercel.com → **Add New Project** → оберіть репозиторій.
3. Найпростіше — встановіть офіційну **Supabase**-інтеграцію Vercel
   (Vercel → Integrations → Supabase): вона сама підставить
   `NEXT_PUBLIC_SUPABASE_URL` і `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Або додайте
   ці дві змінні вручну в Project Settings → Environment Variables.
4. **Deploy**.
5. У Supabase Dashboard → Authentication → URL Configuration додайте адресу
   вашого Vercel-домену в **Redirect URLs** (потрібно для коректної роботи
   посилання підтвердження email).

## Захист публічних статей (опційно)

Без додаткових налаштувань додавати/редагувати/видаляти статті може будь-хто,
хто знає адресу сайту (це навмисно — статті задумані як спільна публічна
база). Щоб обмежити запис спільним секретом:

1. Vercel → Settings → Environment Variables → додайте `ADMIN_TOKEN`.
2. На сторінці `/new` (вкладка «стаття») та на сторінці редагування статті
   з'явиться поле «токен редагування» — введіть те саме значення один раз,
   воно збережеться в `localStorage` браузера.

Це не стосується інструментів і заміток — їх захищає справжня авторизація
Supabase, а не спільний токен.

## Структура проєкту

```
supabase/schema.sql          — SQL-схема: таблиці + RLS-політики

lib/
  supabase/client.ts          — Supabase client для браузера (Client Components)
  supabase/server.ts          — Supabase client для сервера (cookies-based сесія)
  articles.ts                  — статичні .md-статті + публічна таблиця articles
  tools.ts                      — статичний каталог tools.json + приватна таблиця tools
  notes.ts                       — приватна таблиця notes
  commands.ts                     — статичні групи команд + команди з власних tools
  categories.ts                    — списки категорій для select-форм
  types.ts                          — усі спільні TypeScript-типи
  authGuard.ts                       — опційна перевірка ADMIN_TOKEN (тільки статті)
  markdown.ts, slugify.ts, search.ts, api-client.ts

app/
  layout.tsx                  — кореневий layout; стійкий до недоступності Supabase
  error.tsx, global-error.tsx  — тематичні екрани помилок замість голого 500
  login/, signup/               — сторінки входу/реєстрації
  auth/actions.ts                — Server Actions: login, signup, signOut
  auth/confirm/route.ts           — обробка посилання підтвердження email
  new/                              — форма додавання (стаття / інструмент / замітка)
  articles/, tools/, notes/, commands/, roadmap/, saved/
  api/articles|tools|notes/         — REST-роути (POST на колекції, PUT/DELETE за [id])

proxy.ts                      — (заміна middleware.ts у Next.js 16) оновлює сесію
                                  Supabase і редіректить неавторизованих із /notes
                                  та сторінок редагування tools/notes на /login

content/
  articles/*.md, tools/tools.json, commands/commands.json, roadmap/roadmap.json
                               — вбудований базовий контент, видний усім завжди
```

## Чому саме так

**Next.js 16 / React 19 / TypeScript.** Початково я обрав Next.js 14 і JavaScript
як консервативний, швидкий у розробці варіант. Next 14 вже вийшов з підтримки
(EOL, жовтень 2025) — для публічного сайту це реальний ризик безпеки, тому
проєкт оновлено до поточної LTS. TypeScript додано через ту саму причину: коли
з'явились форми, API-роути й авторизація, типи почали давати реальну користь
(лови́ти неузгодженості між формою й API ще до рантайму).

**Supabase (Postgres + Auth), а не файли/KV.** Попередня версія писала
кастомний контент у Vercel KV або локальний JSON-файл — це працювало, але не
підтримувало концепцію «власник запису». Авторизація вимагала справжньої бази
з ізоляцією даних на рівні рядків, тож Postgres із Row Level Security — це не
просто «база даних», а механізм, який гарантує приватність tools/notes навіть
якщо в коді застосунку колись з'явиться помилка: RLS блокує чужі дані на рівні
самого запиту до бази, не покладаючись на те, що фронтенд/API «не забудуть»
перевірити власника.

**`proxy.ts`, а не `middleware.ts`.** Next.js 16 перейменував middleware на
proxy — це не стилістичний вибір, а вимога нової версії.

## Обмеження, про які варто знати

- Локальний dev тепер **вимагає** налаштованого Supabase-проєкту (безкоштовного
  вистачає) — на відміну від попередньої версії, тут більше немає офлайн-режиму
  «просто на локальному файлі», бо авторизація не має сенсу без реальної бази.
- Якщо Supabase тимчасово недоступний, кореневий layout і сторінки, що не
  залежать від бази (`/roadmap`, `/login`, `/signup`, 404), продовжують
  працювати — але сторінки, яким справді потрібні дані (статті, інструменти,
  замітки), покажуть тематичний екран помилки (`app/error.tsx`) замість
  вмісту, поки з'єднання не відновиться.
- Прогрес по roadmap і закладки на статті — досі в `localStorage` браузера
  (не в Supabase), тому не синхронізуються між пристроями. Це свідоме рішення:
  ці дані не приватні у сенсі безпеки, і зберігати їх у базі заради двох полів
  не було сенсу.
